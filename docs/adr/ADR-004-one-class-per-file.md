# ADR-004: Принцип "один класс на один файл"

## Статус

Принято (Accepted)

## Контекст

Необходимо определить правила организации кода в проекте. В Python существуют разные подходы:
- Множество классов в одном файле
- Один класс на файл
- Функциональный подход без классов

Проект следует принципам ООП и KISS.

## Решение

Строго следовать принципу **"один класс = один файл"**.

### Правила

1. Каждый класс располагается в отдельном файле
2. Имя файла совпадает с назначением класса (snake_case)
3. Имя класса в PascalCase
4. Исключение: точка входа `__main__.py` (без класса)

### Структура модулей

```
bot/
├── config.py          → Config
├── bot.py             → TelegramBot
├── llm_client.py      → LLMClient
├── conversation.py    → ConversationManager
└── handlers.py        → MessageHandler
```

## Последствия

### Положительные
- ✅ Максимальная читаемость кода
- ✅ Простая навигация по проекту
- ✅ Понятная структура для новых разработчиков
- ✅ Легко найти нужный класс по имени файла
- ✅ Следует принципу единственной ответственности (SRP)
- ✅ Упрощает code review

### Отрицательные
- ⚠️ Больше файлов в проекте
- ⚠️ Больше импортов между модулями

### Почему это важно для MVP

Несмотря на то, что это MVP, четкая структура:
- Ускоряет разработку (не нужно искать классы внутри файлов)
- Облегчает рефакторинг
- Предотвращает god-objects
- Упрощает будущее расширение

## Альтернативы

1. **Группировка связанных классов в файлы** - отклонена (размывает границы ответственности)
2. **Функциональный подход** - отклонен (проект следует ООП принципам)
