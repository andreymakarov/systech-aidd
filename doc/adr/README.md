# Architecture Decision Records (ADR)

Этот каталог содержит записи архитектурных решений (ADR) для проекта LLM-ассистент.

## Что такое ADR?

Architecture Decision Record (ADR) - это документ, который описывает важное архитектурное решение, принятое в проекте, вместе с его контекстом и последствиями.

## Формат ADR

Каждый ADR следует единому формату:

- **Статус** - Принято (Accepted), Отклонено (Rejected), Устарело (Deprecated), Заменено (Superseded)
- **Контекст** - Описание проблемы и факторов, влияющих на решение
- **Решение** - Описание принятого решения
- **Последствия** - Положительные и отрицательные эффекты решения

## Список ADR

### ADR-001: [Выбор технологического стека](ADR-001-technology-stack.md)
Выбор Python, uv, aiogram, openai, OpenRouter как основного стека технологий.

**Ключевое решение:** Python 3.11+ с uv для управления зависимостями, aiogram для Telegram Bot, openai client для LLM через OpenRouter.

---

### ADR-002: [Использование Polling вместо Webhooks](ADR-002-polling-over-webhooks.md)
Выбор метода polling для получения обновлений от Telegram.

**Ключевое решение:** Polling для простоты развертывания и разработки MVP.

---

### ADR-003: [Хранение истории диалогов в памяти](ADR-003-in-memory-conversation-storage.md)
Решение хранить историю диалогов в оперативной памяти без персистентности.

**Ключевое решение:** In-memory хранилище (`dict[int, list[dict]]`) без базы данных.

---

### ADR-004: [Принцип "один класс на один файл"](ADR-004-one-class-per-file.md)
Организация кода с строгим правилом: один класс в одном файле.

**Ключевое решение:** 1 класс = 1 файл для максимальной читаемости и простоты навигации.

---

### ADR-005: [Отсутствие ограничения контекста диалога](ADR-005-no-context-limit.md)
Решение не ограничивать количество сообщений в истории диалога.

**Ключевое решение:** Вся история отправляется в LLM без ограничений (до лимитов модели).

---

### ADR-006: [OpenRouter как провайдер LLM](ADR-006-openrouter-as-llm-provider.md)
Выбор OpenRouter как единого провайдера для доступа к LLM моделям.

**Ключевое решение:** OpenRouter с моделью `openai/gpt-4o-mini` по умолчанию для гибкости и простоты.

---

### ADR-007: [Конфигурация через переменные окружения](ADR-007-env-based-configuration.md)
Использование `.env` файла для всех настроек приложения.

**Ключевое решение:** Все конфигурации через переменные окружения, загружаемые из `.env` файла.

---

### ADR-008: [Отказ от тестов на этапе MVP](ADR-008-no-tests-for-mvp.md)
Решение не писать автоматизированные тесты для MVP.

**Ключевое решение:** Ручное тестирование для ускорения разработки MVP.

---

### ADR-009: [Отказ от streaming ответов LLM](ADR-009-no-streaming-responses.md)
Решение не использовать streaming режим для ответов LLM.

**Ключевое решение:** Получение полного ответа целиком для простоты реализации.

---

## Процесс принятия решений

1. Выявление архитектурно значимого решения
2. Обсуждение альтернатив и контекста
3. Принятие решения
4. Документирование в виде ADR
5. Коммит ADR в репозиторий

## Изменение решений

Если решение изменяется:
1. Старый ADR получает статус "Superseded" с ссылкой на новый ADR
2. Создается новый ADR с новым решением
3. Старый ADR не удаляется (история решений важна)

## Принципы

Все решения в проекте следуют:
- ✅ **KISS** - максимальная простота
- ✅ **MVP-first** - скорость разработки важнее совершенства
- ✅ **ООП с ограничениями** - 1 класс = 1 файл
- ✅ **Fail fast** - ошибки должны быть явными
- ✅ **Простота** - никакого оверинжиниринга
