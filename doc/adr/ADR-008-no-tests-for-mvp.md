# ADR-008: Отказ от тестов на этапе MVP

## Статус

Принято (Accepted)

## Контекст

Необходимо решить, нужны ли автоматизированные тесты на этапе создания MVP. Обычно рекомендуются:
- Unit тесты
- Integration тесты
- E2E тесты

Но проект следует принципу KISS и ориентирован на быструю проверку концепции.

## Решение

**Не писать автоматизированные тесты** на этапе MVP.

### Обоснование

1. **Скорость разработки** - фокус на функциональности
2. **Простота кода** - код настолько прост, что легко проверяется вручную
3. **Частые изменения** - архитектура может сильно измениться
4. **Малый scope** - всего 6 классов
5. **MVP цель** - проверка концепции, а не production-ready код

### Альтернатива тестам

- **Ручное тестирование** через реального бота
- **Быстрые итерации** и исправление багов
- **Простой код** легко читается и проверяется review

## Последствия

### Положительные
- ✅ Быстрая разработка
- ✅ Нет overhead на поддержку тестов
- ✅ Не нужна настройка test framework
- ✅ Фокус на функциональности, а не на coverage
- ✅ Меньше кода для написания и поддержки

### Отрицательные
- ⚠️ Нет автоматической проверки регрессий
- ⚠️ Потенциально больше багов в production
- ⚠️ Сложнее рефакторинг (нет safety net)
- ⚠️ Нужно больше времени на ручное тестирование

### Приемлемость для MVP

Для проверки концепции отсутствие тестов **приемлемо**:
- Небольшой scope проекта
- Быстрые итерации важнее стабильности
- Легко откатить изменения (git)
- Код простой и читаемый

### Когда добавить тесты

Тесты станут необходимы при:
1. Переходе от MVP к production
2. Увеличении команды разработки
3. Усложнении бизнес-логики
4. Необходимости CI/CD
5. Активном использовании ботом

## Альтернативы

1. **Unit тесты для критичной логики** - отклонено (вся логика простая)
2. **Integration тесты** - отклонено (требует mock'ов Telegram и OpenRouter)
3. **E2E тесты** - отклонено (сложная настройка для MVP)

## Компромисс

При необходимости позже легко добавить тесты:
- Код написан с учетом Dependency Injection
- Классы изолированы (легко мокировать)
- Простая архитектура (легко покрыть тестами)
